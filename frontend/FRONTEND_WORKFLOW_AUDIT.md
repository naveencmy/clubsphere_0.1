# Frontend workflow coverage audit

Scope: React/Vite frontend prototype, based on the official Skyline problem statement, repository PRD, implementation plan, architecture blueprint, attached master specification and mandatory DESIGN.md override. No production backend, SQL, database policy or payment infrastructure was changed.

Status meanings: PASS indicates implemented behavior with executed service/browser evidence; NOT VERIFIED identifies behavior that needs physical-device or external integration verification. A service test does not assert that every possible UI variation has been manually exercised. Route rendering is reported separately from completed transactions.

## Executed validation and evidence

- `tests/workflows.test.js`: all six official Skyline service journeys plus domain safeguards were executed and passed.
- `tests/edge-cases.test.js`: profile privilege protection, repeated late callbacks, reservation-safe inventory edits, scanner assignment denial, donation idempotency, officer handover, actual negative order states and shared fundraiser health passed. A regression test additionally covers undefined IDs in create-form payloads.
- `tests/browser/frontend.spec.js`: membership/ticket/persistence, merchandise checkout, mobile navigation/club isolation, scanner dismissal/timing, task status movement and 26 rendered accessibility captures passed.
- `tests/browser/design-interactions.spec.js`: scanner geometry/feedback invocation, ledger hover/selection/focus, drag/drop styling and reduced motion passed.
- `tests/browser/navigation.spec.js`: 74 route/role combinations rendered without uncaught errors; 320/768/1024/1280px checks passed. Evidence: `artifacts/route-audit.json` and `artifacts/breakpoint-audit.json`.
- `tests/browser/management.spec.js`: all three tests passed, covering ledger CSV export, announcement preview/publish/delivery/read, and receipt upload/approval/payout. The generated-ID regression is corrected and covered by a service test.
- `npm run build`: production bundling passed; chart, form and QR libraries use separate chunks.
- Final validation on 2026-10-10: 23 service tests and 15 Chrome browser tests passed. Browser tests ran against the built production preview. Production build and `npm run format:check` passed after multiline source formatting.

## Findings corrected during implementation

1. Mobile Kanban overflow, undersized icon targets, unnamed progress bars and an unfocusable empty table region were corrected after rendered inspection.
2. Scanner centering and modal placement were corrected against exact DESIGN geometry.
3. Negative zero in an empty payable summary was normalized.
4. Profile mutation cannot change role or internal user ID; scanner volunteers need explicit assignment; stock edits cannot erase active holds; repeated late callbacks and donation requests cannot double-post effects.
5. Fundraiser health now derives from all campaign preparation records before role-specific task filtering.
6. Real create forms included `id: undefined`; generic record copying erased generated IDs. Services now preserve immutable identity/tenant/history/status fields and copy only defined editable values, with task status handled explicitly.

## Transparent integration limits

All identity, permission, checkout, payment confirmation, notification dispatch, refund, accounting and payout operations are local demonstrations. Real authorization, signed passes, cross-device reservations, gateway callbacks, email providers and bank transfers require the future backend. Physical camera/audio/vibration remain NOT VERIFIED. These limits are displayed in the UI and do not represent unfinished production backend work within this frontend-only task.

## Authentication update — 2026-10-10

Identity now uses Better Auth with email/password, optional Google OAuth and PostgreSQL HTTP-only sessions. The current identity, club roles and route guards require a verified server session. Self-registration cannot request elevated system roles. Existing bcrypt accounts are normalized for Better Auth compatibility. Three real-database integration checks and three browser auth checks passed. Google consent/callback completion remains unverified pending private provider credentials. Earlier local demo sign-in audit results describe the historical prototype. Business workflows retain their existing adapters.
